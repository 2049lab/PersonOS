# 框架设计

[← PersonOS](../README.zh-CN.md) · [English](framework.md) · 简体中文 · [API 指南](usage.zh-CN.md)

PersonOS 从应用提交的资料中形成关于一个人的长期记忆。应用决定资料来源和所属用户，框架负责保留证据、提取相关记忆并支持后续检索。

## 记忆范围

文本写入判断一段内容是否帮助了解用户的处境、关系、偏好、目标、计划、承诺或经历。正在推进的项目、有依据的工作偏好可以成为记忆。执行任务的指令、助手的实施步骤、尚未采纳的建议，以及与用户无关的第三方故事，都不能直接成为个人事实。

归属必须有依据。助手的建议只有在对话支持用户采纳或认可时，才能作为关于用户的证据。推断需要明确标注，并以 `claim` 保存；情景正文只记来源能够支持的内容。深度召回的回写工具范围更窄：可以保留明确陈述的个人事实、计划与观点，不应将新推断写入记忆或情景正文。

应用可以通过 `scenario` 调整关注点，例如更多关注饮食偏好。它只能在个人记忆范围内收窄关注，不能把无关任务内容变成用户事实。

这些规则通过提示词和解析逻辑落实，不能保证所有模型都能正确判断每段对话。原始证据仍需保留，供检查与评测使用。

## 记忆分层

| 层 | 职责 | 保留什么 |
|---|---|---|
| 原始证据（Evidence） | 保存来源 | 原话、时间与媒体引用 |
| 情景（`MemCell`） | 保留个人事件的上下文 | 叙述、主题、时间范围与证据引用 |
| 原子记忆（`MemoryAtom`） | 支持事实检索 | 含适用条件的陈述、归属，以及情景和证据引用 |
| 记忆链（`ChainInfo`） | 关联相关陈述 | 不同观察之间的关联与追加顺序 |
| 用户画像（Profile） | 整理对用户的认识 | 根据积累的情景生成的派生画像 |

检索先找到原子记忆，再组织相应情景作为回答材料。记忆链关联相关观察，不覆盖较早记录。回答涉及事实变化时，需要结合陈述的时间和上下文判断。

文本提取可以不生成情景，也可以生成没有原子记忆的情景。两种情况下都保留原始证据。没有原子的情景仍可通过情景列表查看，不会为了让检索命中它而额外制造一个兜底原子。

情景生成失败时，写入流程保留证据并跳过派生情景，不会直接把整段原文当成个人记忆。提取失败或跳过，与成功形成记忆是不同结果；队列消费完成本身不能证明记忆质量。

## 读取方式

| 操作 | 使用模型的环节 | 适用场景 |
|---|---|---|
| `list_memories`、`list_chains`、`get_chain` | 无 | 检查已保存记录、构建记忆浏览器、核对来源 |
| `search(mode="flash")` | 向量化与可选重排 | 让 Agent 获取材料并自行组织回答 |
| `search(mode="fast")` | 查询处理、检索、回答生成与复核 | 提问并获得关联证据的答案 |
| `search(mode="auto")` | 快速召回，必要时尝试深度召回 | 在已安装深度召回时按需使用 |
| `search(mode="deep")` | 模型驱动的多步检索 | 探索快速路径之外的记忆，需要 `deep` 扩展 |

`flash` 返回检索候选，不生成答案，也不提供答案复核结论。应用不应将这些候选直接展示为已经证实的结论。结果字段和使用限制见 [API 指南](usage.zh-CN.md#召回与溯源)。

浏览接口限定用户范围与单页大小。记忆链目录只返回元数据，需要查看历史时再读取链详情。发现历史不完整或读取期间发生变化时，详情接口会明确返回状态，不会补造连续时间线。

## 本次框架升级

本次从已有能力中选取适合通用记忆框架的部分，继续保留 SQLite 与可配置模型服务作为默认开发路径。

| 能力 | 本次处理 | 原因 |
|---|---|---|
| 个人记忆提取与合法空结果 | 已纳入 | 避免将没有个人信息的对话强行生成记忆 |
| 证据身份 | 已纳入 | 不同消息可能包含相同文字，应通过记录 ID 判断重试 |
| 分页浏览记忆与记忆链 | 已纳入 | 无需额外调用模型，也无需一次返回完整历史 |
| 只返回材料的召回 | 已纳入 | 由接入方 Agent 决定如何生成答案 |
| 可声明标签词表 | 暂缓 | 需要统一公开字段、过滤语义及各写入路径的失败处理 |
| 直接提交情景 | 暂缓 | 需要明确调用方撰写内容和缺少原始证据时的接口约定 |
| 按会话删除 | 暂缓 | 需要一致处理画像、队列、派生记忆链与媒体引用 |
| 更多向量存储后端 | 暂缓 | 需要可选后端接口和迁移测试，不能破坏本地默认体验 |
| 应用专用设备流程 | 留在核心之外 | 应由适配层或应用维护各自依赖与部署条件 |

已有的可选图片和视频后端继续保留。它们有独立的依赖、处理流程与模型要求；本次更新不构成新的视频准确率结论。

### 兼容性说明

- 原有 SDK 方法与召回模式继续保留，浏览方法和 `flash` 为新增接口。
- 所有召回模式现在都校验非空查询、有效模式，以及 1–100 范围内的整数 `top_k`；布尔值不作为整数接受。无效值在 SDK 中抛出 `ValueError`；HTTP 类型校验错误返回 `422`，无效模式或越界整数返回 `400`。
- 文本提取现在接受空结果。接入方不能假定每次提交都会形成情景，或至少产生一个原子记忆。
- 新证据按消息身份区分，不再仅按文字内容区分。不同消息中的相同文字会分别保留；存储层使用同一个记录 ID 重试追加时保持幂等。这不等于应用全链路保证消息只处理一次。
- 已按内容合并的历史记录不会自动拆分、重抽或迁移。新规则作用于后续写入。
- 跳过个人记忆提取时仍保存原始证据，跳过记忆不等于删除来源。
- 历史 benchmark 分数早于本次修改。单元测试验证行为和用户隔离，不代表已经重新验证这些评测中的提取与召回质量。

新 API 的文档以当前源码为准。只有包含这些修改的版本正式构建并上传后，已发布安装包才会包含相应能力。

## 存储与部署

Python API 按 `user_id` 限定记忆操作，应用需要把它绑定到已认证用户。HTTP 服务先解析用户 token，再处理记忆操作。客户端自行传入一个用户 ID，本身不能构成授权规则。

单进程可以使用 SQLite 与进程内会话状态。多进程需要共享 MySQL 和 Redis。本地存储不代表本地推理，内容会发送到你配置的模型端点。接入应用需要明确部署、访问控制与数据保留方式。

`reset(user_id=...)` 清理已保存记录及部分进程内会话状态，不覆盖待处理队列、外部媒体和模型服务端数据，不能将它描述为完整的数据擦除流程。
